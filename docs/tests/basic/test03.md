**1.** Команда `git push --force` отклонена — на удалённой ветке `main` включена защита (`branch protection`). Разработчик хочет переписать историю (удалить коммит с секретом). Какой подход корректен?

- A) Отключить branch protection, сделать `--force`, сразу включить обратно — это стандартная процедура
- B) Использовать `git push --force-with-lease` — обходит любые защиты ветки
- C) Создать новую ветку с очищенной историей через `git filter-repo`, открыть PR — branch protection не обходится, история переписывается через штатный процесс ревью
- D) Сделать `git revert` — это равнозначно удалению коммита из истории

**2.** Какой сигнал отправляет команда `kill -9 <PID>`?

- A) SIGTERM — запрос на корректное завершение
- B) SIGHUP — перечитать конфигурацию
- C) SIGKILL — принудительное немедленное завершение
- D) SIGSTOP — приостановка процесса

**3.** Nmap сканирует хост: порт `8080/tcp open http-proxy`. Какой следующий шаг наиболее информативен для оценки поверхности атаки через этот сервис?

- A) Запустить `nmap -sU` на порт 8080 — UDP даст дополнительный контекст
- B) Запустить `nmap -sV --script=http-methods,http-headers,http-title -p 8080 <host>` — определить версию ПО, разрешённые методы и заголовки безопасности
- C) Запустить полный TCP Connect scan `-sT -p-` повторно — первое сканирование могло пропустить порты
- D) Результата SYN-сканирования достаточно — дополнительная информация не нужна

**4.** Контейнер в production потребляет 100% CPU и вызывает деградацию соседних сервисов на том же хосте. В `docker-compose.yml` нет ограничений ресурсов. Какая конфигурация корректно решит проблему?

- A) `mem_limit: 512m` — ограничение памяти автоматически ограничивает CPU
- B) `cpus: "0.5"` и `mem_limit: 512m` через `deploy.resources.limits` — cgroups v2 ограничит контейнер 50% одного ядра и 512 МБ RAM
- C) `restart: unless-stopped` — контейнер перезапустится при высокой нагрузке
- D) Перенести контейнер на отдельный хост — ограничение ресурсов в Docker ненадёжно

**5.** Trivy сканирует образ и выдаёт 47 CVE, из которых 3 критических. Все критические — в пакете `libssl3` базового образа `debian:bookworm-slim`. Команда не может обновить базовый образ из-за совместимости. Какой подход снижает риск без смены базового образа?

- A) Добавить все 47 CVE в `.trivyignore` — команда осознанно принимает риск
- B) `RUN apt-get update && apt-get upgrade -y libssl3` в Dockerfile — пропатчить только уязвимый пакет внутри образа
- C) Переключиться на `--severity HIGH` — игнорировать CRITICAL, это снизит шум
- D) Отключить Trivy в CI — сканирование блокирует деплой без пользы

**9.** В `docker-compose.yml` смонтирован том `/var/run/docker.sock:/var/run/docker.sock` внутрь контейнера приложения. Какую критическую угрозу это создаёт?

- A) Приложение сможет читать логи других контейнеров, но не управлять ими
- B) Контейнер получает возможность создавать новые контейнеры с флагом `--privileged` и монтированием файловой системы хоста — фактически полный побег из изоляции
- C) Это стандартная практика для микросервисов, угроза минимальна
- D) Монтирование docker.sock замедляет I/O контейнера из-за конкуренции за ресурс

**10.** Компания хранит данные клиентов в self-hosted PostgreSQL. После аудита выявлен риск утечки из-за отсутствия шифрования at-rest и слабого backup. Бюджет ограничен. CTO предлагает мигрировать в managed AWS RDS с encryption и автобэкапами. Какая стратегия управления риском применяется?

- A) Risk Avoidance — компания отказывается от хранения данных
- B) Risk Mitigation — внедряются технические меры снижения вероятности
- C) Risk Transfer — ответственность за инфраструктурную безопасность (шифрование, бэкапы, патчинг ОС) передаётся AWS, но ответственность за данные и конфигурацию остаётся на компании
- D) Risk Acceptance — миграция в облако означает принятие всех рисков AWS
