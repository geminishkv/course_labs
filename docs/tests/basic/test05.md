- A) Прочитать файлы в `/var/www/html`, доступные `www-data`
- B) Установить `setuid`-бинарь в `/tmp` и запустить его

**3.** Semgrep находит в Flask-приложении следующий код:

```python
result = eval(request.args.get("formula"))
```

Разработчик утверждает: «`eval` безопасен, если передавать только математические выражения». Что является корректным контраргументом?

- A) `eval` безопасен при использовании HTTPS — данные зашифрованы при передаче
- B) Проблема только в отсутствии валидации входных данных — достаточно проверить тип
- C) `eval` выполняет произвольный Python-код: `__import__('os').system('id')` — легитимное с виду «выражение» даёт RCE; ввод контролируется атакующим, не сервером
- D) `eval` небезопасен только при использовании в Python 2, в Python 3 он безопасен

**9.** При оценке риска используется формула `Риск = Вероятность × Ущерб`. Уязвимость имеет высокий ущерб (9/10), но низкую вероятность эксплуатации (1/10). Итоговый риск — 9. Соседняя уязвимость: ущерб 4/10, вероятность 8/10, риск — 32. Как приоритизировать устранение и почему простая сортировка по ущербу ошибочна?

- A) Приоритет — первая (ущерб 9), так как потенциальные последствия критичнее
- B) Обе уязвимости равнозначны — нужно устранять в порядке поступления
- C) Приоритет — вторая (риск 32): реальная угроза определяется произведением вероятности и ущерба; высокоэксплуатируемые уязвимости со средним ущербом чаще приводят к инцидентам, чем теоретически опасные, но труднодостижимые
- D) Метрики вероятности ненадёжны — нужно ориентироваться только на ущерб
