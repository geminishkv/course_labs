## Вопросы

**1.** Финтех-компания внедряет Open Banking API для обмена данными о счетах клиентов с партнёрами. Опишите модель угроз для этого сценария: минимум 3 вектора атаки, для каждого — CWE, влияние на бизнес и мера снижения. Учтите требования 152-ФЗ к передаче ПДн третьей стороне.

**2.** Почему обычного DevSecOps недостаточно для финтех-продуктов? Сравните Quality Gate для e-commerce приложения и для платёжного шлюза: какие дополнительные проверки нужны в CI/CD пайплайне финтеха? Приведите конкретные примеры SAST/SCA/DAST правил, специфичных для финансового кода.

**3.** Цифровой рубль запускается с сентября 2026. Крупнейшие банки обязаны его принимать. Опишите: какие новые attack surfaces появляются при интеграции цифрового рубля в существующую платёжную инфраструктуру? Какие требования ЦБ РФ к безопасности участников пилота? Как это влияет на архитектуру AppSec.

**4.** Компания прошла аудит по ГОСТ Р 57580.1 и получила оценку уровня соответствия 0.7 (при минимально допустимом 0.85). ЦБ выдал предписание на устранение за 90 дней. Составьте план действий: какие категории проверок (Host, Daemon, Images, Runtime, Ops) приоритизировать, какие инструменты использовать (Trivy, Docker Bench, Checkov), какие метрики отслеживать.

**5.** Кейс: в публичный GitHub-репозиторий финтех-стартапа попал API-ключ платёжного шлюза. Бот обнаружил его через 47 секунд после push. Опишите порядок реагирования по шагам (Incident Response): немедленные действия, ротация, анализ ущерба, уведомление регуляторов, пост-мортем. Какие штрафы грозят по 115-ФЗ и PCI DSS? Как pre-commit hook мог предотвратить инцидент?

## Формат ответов

> Ответы оформляются в `gist`-отчёте. Каждый ответ — развёрнутый (5–10 предложений), с конкретными ссылками на законы (115-ФЗ, 152-ФЗ, 187-ФЗ), стандарты (ГОСТ 57580, PCI DSS), CWE-ID и примерами из практики.
